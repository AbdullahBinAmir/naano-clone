## 2. Design System Approach — Dark Liquid-Glass Theme

### 2.1 Token layer
Define design tokens in `globals.css` using Tailwind v4's `@theme` block: a restrained dark palette (near-black base `#0a0a0c`–`#111114`, elevated surface tones a few % lighter for card stacking, one accent hue for CTAs/brand — naano's own brand green/teal is a reasonable reference point, but this should be an intentionally chosen accent, not copied pixel-for-pixel), plus glass-specific tokens: `--glass-bg` (very low-opacity white/near-white, e.g. `rgba(255,255,255,0.06)`), `--glass-border` (`rgba(255,255,255,0.12)`), `--glass-blur` (e.g. `18px`), `--glass-saturate` (`160%`+ to keep translucent panels from looking muddy over the dark background). This directly operationalizes the `apple-design` skill's translucent-materials guidance (Apple's frosted-glass "material" approach: `backdrop-filter: blur() saturate()` over a semi-transparent fill, layered on a busy/gradient background so the blur has something to distort) using only CSS + Tailwind — no invented "liquid glass" component library is assumed.

### 2.2 Primitive layer
- Base UI provides unstyled, accessible primitives (Dialog, Popover, Tabs, Select, Tooltip, etc.) — wrap each in `src/components/ui/` with the project's glass/dark styling applied via Tailwind + `cva` variants. This mirrors the shadcn pattern (own-your-components, not a black-box library) which is what `pick-ui-library` steers toward, and keeps every primitive themeable in one place.
- Build a small set of composable glass surfaces in `src/components/glass/`: `GlassPanel` (base card), `GlassCard` (panel + hover-lift + border-glow, for creator card preview and stat tiles), `GlassNav` (sidebar/topbar variant with heavier blur since it sits over scrolling content). These wrap the token layer so no page hand-rolls `backdrop-filter` inline.
- Motion is used for: page/section entrance transitions, sidebar active-indicator sliding underline, checklist step completion, card-flip/hover states on the creator-card preview, tab-switch transitions in Collaborations, and the floating AI bar's expand/collapse. `animation-vocabulary` should be used to name these consistently in code comments/commit messages (e.g. "ease-out settle", not vague "smooth animation") so future contributors reuse the same motion language.
- NumberFlow drives every stat tile with a numeric value that changes (Overview's reach/engagement counts, wallet balance, Earnings tiles) — even in Phase 1 with static demo numbers, animating count-up on mount/tab-focus is a low-cost, high-perceived-quality win the skills explicitly call out.
- Sonner (via `ask-sonner`) handles all transient feedback: "Link copied", "Withdrawal requested" (Phase 1: fake/optimistic), form validation errors.
- cmdk powers the floating "What can I help you find?" bar's interaction shell in Phase 1 (see §3.5) even before it's wired to a real assistant — cmdk gives keyboard-navigable, filterable command-list UX for free, which can list canned quick actions/navigation shortcuts.

### 2.3 Scaling across ~9 creator pages + brand + public pages
- Every dashboard page composes from the same shell: `PageHeader` (title + primary action), a grid of `GlassCard`s, and, where tabular, a shared `DataTable`-style component (used identically by Collaborations and later by Opportunities/brand Campaigns) — building this once in Phase 1 avoids 9x bespoke table implementations.
- Co-locate module-specific components under `components/creator/&lt;module&gt;/` so each of the 9 sections is independently extendable without cross-module coupling — this matters because Phases 3–9 will replace each module's data layer independently and shouldn't risk regressing sibling modules.
- Public creator-card pages (`(public)/creators/[handle]`) and the in-dashboard "My card" editor/preview should share the actual card-rendering component (`CreatorCardPreview`) so the creator always sees a WYSIWYG preview of what brands/public visitors see — critical since the product's core mechanic (the "deal link") depends on that card looking identical whether viewed by its owner or an external visitor.

### 3.2 Demo content strategy — recommendation: **typed demo-data module now, Supabase seed SQL migration path later, not a permanent split**

Two candidate approaches were weighed:
1. **Local mock JSON/TS module** (`lib/demo-data/*.ts`) imported directly by Server/Client Components.
2. **Seeded Supabase tables, read via the real Supabase client, with RLS relaxed/scoped for demo rows.**

**Recommendation: start with (1), but design the TypeScript types in `demo-data/` to be byte-for-byte identical to the Phase 2+ Supabase row shapes (derived from the schema in §4).** Rationale:
- Phase 1 explicitly has "no real backend wiring" — standing up Supabase, migrations, and RLS purely to serve static demo content would be premature infrastructure investment before auth/schema are finalized, and would risk needing rework once real RLS policies are designed in Phase 2.
- A local `lib/demo-data/index.ts` (with per-domain files: `creators.ts`, `collaborations.ts`, `earnings.ts`, `messages.ts`, `affiliate.ts`, `analytics.ts`, `brands.ts`) lets every page be a Server Component that does `const creator = await getDemoCreator(handle)` — an async function signature identical to what the real Supabase-backed version will have in Phase 3+ (`getCreatorByHandle(supabase, handle)`), so swapping the data source later is a one-line change per call site, not a rewrite.
- Once Phase 2 stands up the real schema, the *same* demo dataset gets promoted into `supabase/seed.sql` (or a seed script using the Supabase JS client with the service role key, run locally/in CI) so local dev and demo/staging environments have realistic data from day one — this reuses the Phase 1 authoring effort rather than discarding it.
- This avoids the trap of building RLS policies for "demo mode" that would need to be torn out or reconciled with real multi-tenant RLS later.

Include a `lib/demo-data/index.ts` export of 2–3 creator personas (e.g. one under the 1,000-follower threshold showing locked states, one over showing unlocked Opportunities/visible-on-Marketplace states, one with zero collaborations for empty-state coverage) and at least one brand persona, so every conditional UI state enumerated in §3.1 is reachable by switching a `?demoAs=` query param or a small in-app "Demo persona" switcher in the topbar (dev-only, hidden/removed once Phase 2 auth lands).

### 3.4 Asset sourcing (Unsplash + free stock video)
- **Images**: use Unsplash. Two viable methods — (a) the Unsplash API (`api.unsplash.com`) with a registered application ID, fetched at build time or via `next/image` with a remote loader, which keeps images fresh but adds a runtime dependency and rate limits (demo-tier: 50 req/hour, which is fine for build-time fetches but risky for live client-side fetches); or (b) manually curate and download a fixed set of images (avatars, banner/hero imagery, category placeholder photos) into `public/images/`, referenced statically. **Recommend (b) for Phase 1** — deterministic, no external network dependency for the demo to render, no rate-limit risk during stakeholder review sessions, and avatars/banners for fictional demo creators shouldn't change between sessions anyway. Store an `ATTRIBUTIONS.md` (or a `public/images/CREDITS.md`) mapping each downloaded file to its Unsplash photographer/photo URL — Unsplash's license doesn't legally require attribution but crediting is good practice and Unsplash's guidelines ask that you not imply endorsement or resell the photos as-is; downloading via their standard "Download" flow (not hotlinking/scraping) keeps this compliant.
- **Video**: source hero/marketing background video from Pexels (or Coverr) under their respective free-to-use licenses; download and self-host in `public/video/` (compressed, muted autoplay loop, `poster` fallback image) rather than hotlinking, for reliability and to avoid depending on a third party's CDN uptime for your homepage hero. Record the source URL/license terms per clip similarly in the credits file.
- Both choices should be revisited if the product moves toward *real* creator-submitted photos in later phases (Supabase Storage becomes the asset host at that point, not Unsplash).

## 4. Data Model (Supabase Postgres) — Schema Sketch

This is a guiding sketch to shape Phase 1's demo-data types, not final DDL — exact column types/constraints get finalized when Phase 2 writes real migrations, but the shape below is sufficient to avoid a schema rewrite later.

- **`profiles`** — `id` (uuid, FK to `auth.users.id`), `role` (enum: `creator` | `brand` | `admin`), `email`, `display_name`, `avatar_url`, `locale` (`en`|`fr`), `created_at`.
- **`creator_profiles`** — `profile_id` (FK, 1:1 with profiles where role=creator), `handle` (unique, for public URL), `headline`, `bio`, `category_tags` (text[] or join table `creator_categories`), `follower_count`, `is_marketplace_visible` (bool, derived/cached from follower threshold), `linkedin_public_url`.
- **`creator_cards`** — `id`, `creator_profile_id` (FK), `price_per_post`, `banner_url`, `card_slug` (matches public route), `deal_link_token` (used for attribution tracking), `published_at`.
- **`brand_profiles`** — `profile_id` (FK), `company_name`, `industry`, `plan_tier` (enum: `self_serve` | `managed`), `logo_url`.
- **`campaigns`** — `id`, `brand_profile_id` (FK), `title`, `brief_text`, `budget`, `target_vertical`/ICP filters, `status` (enum: `draft`|`published`|`closed`), `created_at`.
- **`collaborations` (bookings)** — `id`, `campaign_id` (FK, nullable if direct-outreach deal), `creator_profile_id` (FK), `brand_profile_id` (FK), `status` (enum: `applied`|`needs_action`|`active`|`declined`|`completed`), `agreed_price`, `next_action_text`, `due_date`, `performance_snapshot` (jsonb), `net_payout_to_creator`, `created_at`.
- **`conversations`** and **`messages`** — `conversations(id, collaboration_id nullable, created_at)`, `conversation_participants(conversation_id, profile_id)`, `messages(id, conversation_id, sender_profile_id, body, created_at, is_system` — for the seeded NaanoBot thread`)`.
- **`earnings_ledger`** — `id`, `creator_profile_id` (FK), `collaboration_id` (FK nullable), `amount`, `type` (enum: `collaboration_payout`|`affiliate_reward`|`referral_bonus`), `status` (enum: `pending`|`in_transit`|`available`|`withdrawn`), `created_at`.
- **`payout_methods`** — `id`, `creator_profile_id` (FK), `method_type` (enum: `bank_transfer`|`stripe_connect`), `bank_account_holder`, `bank_details_encrypted_ref` (never store raw bank details in plaintext — see §6), `stripe_connect_account_id` (nullable), `is_active`.
- **`affiliate_referrals`** — `id`, `referrer_profile_id` (FK), `referred_profile_id` (FK, nullable until claimed), `referral_type` (enum: `invite_brand`|`invite_creator`), `referral_code`, `status` (enum: `pending`|`activated`|`rewarded`|`expired`), `activation_event_at` (for creator-invites: set at *first completed paid collaboration*, not signup — matches the confirmed product rule), `reward_window_ends_at` (activation_event_at + 3 months), `created_at`.
- **`linkedin_analytics_snapshots`** — `id`, `creator_profile_id` (FK), `captured_at`, `public_post_reach`, `public_posts_count`, `public_engagements`, `follower_count`, `pct_posts_with_reach_data`, `source` (enum: `manual_entry`|`csv_upload`|`official_api`|`third_party_provider` — see Phase 4 flag below), `raw_payload` (jsonb).
- **`linkedin_posts`** (child of a snapshot or standalone) — `id`, `creator_profile_id`, `original_post_url`, `posted_at`, `reach`, `engagements`, `has_reach_data` (bool).
- **`notifications`** — `id`, `profile_id`, `type`, `payload` (jsonb), `read_at`, `created_at`.

Cross-cutting: every table that's creator- or brand-owned carries an owner FK suitable for RLS `auth.uid() = owner_id`-style policies (§6). Enums should be Postgres native enums (or check constraints) for query-plan efficiency and to keep the demo-data TS union types trivially mappable to DB values.

## 5. Module-by-Module Phase Breakdown (Post–Phase 1)

**Phase 2 — Auth &amp; Supabase wiring, role-based routing.** Stand up the real Supabase project, run initial migrations from §4, implement `@supabase/ssr` browser/server clients and the middleware session-refresh pattern, replace static sign-in/sign-up with real Supabase Auth (email/password + optionally magic link), implement the role-based route guards in `(dashboard)/creator` vs `(dashboard)/brand` layouts, and replace the Phase 1 "demo persona switcher" with real session-derived role/identity. **Phase 3 — Creator card + public profile pages go dynamic.** Wire "My Card" editor to real `creator_cards`/`creator_profiles` CRUD via Server Actions, make the public `/creators/[handle]` route fetch from Supabase (with appropriate caching/revalidation), implement the deal-link attribution token generation and click/visit tracking that underlies the 25%-for-3-months mechanic's data trail.

**Phase 4 — Analytics / LinkedIn data ingestion.** **Flag clearly**: scraping LinkedIn's public pages to auto-populate `linkedin_analytics_snapshots` violates LinkedIn's Terms of Service; LinkedIn has actively pursued legal action against scrapers (e.g. the hiQ Labs litigation history and subsequent enforcement/IP-blocking practices) and technically blocks/rate-limits scraping traffic, so treat "no personal LinkedIn connection required" marketing language as a UX promise to eventually reproduce **compliantly**, not a mandate to scrape. Recommended alternatives, roughly in order of build effort: (a) **manual entry / CSV upload** — creator pastes their own stats or uploads a LinkedIn-exported analytics CSV, ingested into `linkedin_analytics_snapshots` with `source='csv_upload'` — lowest legal risk, ships fastest; (b) **official LinkedIn API** (Marketing/Community Management APIs) — requires the creator to OAuth-connect and requires LinkedIn partner-program approval, which contradicts the "no connection required" promise but is fully compliant; (c) a **compliant third-party social-analytics data provider** that has its own licensed data-access agreements with LinkedIn — fastest path to the "no connection required" UX, at the cost of a vendor dependency and cost-per-lookup. Recommend shipping (a) first as the real Phase 4 deliverable, and treating (b)/(c) as a follow-on enhancement gated on legal/business sign-off, not something engineering should default into.

**Phase 5 — Opportunities / Collaborations booking flow.** Brand-side campaign publishing, creator-side apply flow, status transitions (`applied`→`needs_action`→`active`→`completed`/`declined`) as Server Actions with RLS-enforced ownership checks, wiring the Collaborations table to real data with the tab filters as real queries.

**Phase 6 — Messaging.** Move `conversations`/`messages` to Supabase Realtime (Postgres changes or Broadcast) for live inbox updates; keep the NaanoBot seeded-thread pattern as a real system-generated conversation created on first booking (matching the confirmed empty-state copy "thread opens with your first Booking").

**Phase 7 — Earnings / payouts.** **Flag clearly**: real Stripe Connect (Express/Custom accounts) involves KYC/identity verification, country eligibility, tax-form collection, and payout-timing/compliance obligations that are substantial scope on their own — recommend building a **simulated internal ledger first** (the `earnings_ledger`/`payout_methods` tables already support `pending`/`in_transit`/`available`/`withdrawn` states purely in-app, with "withdrawal" as a status transition and no real money movement) so the full Earnings UX (tiles, chart, withdraw flow) is demoable and testable before taking on Stripe Connect's onboarding flow, webhook handling, and reconciliation logic as a distinct, later sub-phase (7b).

**Phase 8 — Affiliate program.** Real referral-link generation/redemption, `affiliate_referrals` state machine tied to actual signup + first-completed-paid-collaboration events, plus the fraud/abuse controls detailed in §6.6.

**Phase 9 — Brand-side self-serve portal.** Full Match → Brief → Publish → Pay → Track flow with real campaign creation, creator matching query logic (filter by category/follower/price), and — once Phase 7b's Stripe integration exists — real brand-side payment collection for bookings.

**Phase 10 — AI assistant bar wired to a real LLM.** Replace the Phase 1 canned-response/cmdk-only shell with a real backend (e.g. a Next.js Route Handler streaming a Claude API response, using function-calling/tools to actually query the user's own Supabase data — "what's my wallet balance", "show me needs-action collaborations" — scoped strictly to the authenticated user's own rows via the same RLS boundary as the rest of the app, never a service-role bypass from a user-facing endpoint).

## 6. Security &amp; Platform-Integrity Recommendations

### 6.1 Row Level Security (RLS) patterns per table
- Enable RLS on every table in `public` schema from the first real migration (Phase 2) — no table ships without it, including junction/lookup tables.
- **Ownership pattern** (creator/brand self-service tables — `creator_profiles`, `creator_cards`, `payout_methods`, `earnings_ledger`, `brand_profiles`, `campaigns` drafts): `USING (auth.uid() = profile_id)` for `SELECT`/`UPDATE`/`DELETE`, and a matching `WITH CHECK` on `INSERT`/`UPDATE` so a user can't write a row claiming someone else's `profile_id`.
- **Public-read, owner-write pattern** (`creator_cards` once `published_at IS NOT NULL`, public creator profile fields): a `SELECT` policy with `USING (published_at IS NOT NULL OR auth.uid() = owner_id)` so anonymous/public visitors can read published cards but drafts stay private to the owner — this directly encodes the "not visible on Marketplace yet" business rule at the database layer, not just in UI conditionals, which matters because the public `/creators/[handle]` route and any future public API must not leak unpublished cards regardless of what the frontend chooses to render.
- **Brand-visibility gating on `is_marketplace_visible`**: a `SELECT` policy on the view/table brands query for matching should additionally require `creator_profiles.follower_count &gt;= 1000` (or the cached `is_marketplace_visible` boolean) so a brand can never fetch a below-threshold creator's data through the Match feature even if they guess a handle — this is the RLS-level enforcement of the 1,000-follower Marketplace gate described in the product.
- **Collaboration/message access**: `USING (auth.uid() IN (creator_profile_id, brand_profile_id))` on `collaborations`; for `messages`, join through `conversation_participants` so `USING (EXISTS (SELECT 1 FROM conversation_participants cp WHERE cp.conversation_id = messages.conversation_id AND cp.profile_id = auth.uid()))`.
- **Admin bypass**: admins should **not** get a blanket `role = 'admin'` RLS bypass policy that every table checks (that's a wide, easy-to-misconfigure attack surface if the `profiles.role` value is ever attacker-influenced). Instead, admin operations run through **Server Actions/Route Handlers using the Supabase service-role key**, which bypasses RLS entirely at the client level — and that service-role key must only ever be read from a server-only env var (never `NEXT_PUBLIC_*`), used only inside server-side code, and gated by an application-level check (`profiles.role === 'admin'` verified server-side against the authenticated session) before any privileged query runs.
- Write and test RLS policies with the Supabase SQL editor's policy-testing tools (or `pgTAP`) against representative rows for each role before Phase 2 is considered done — RLS bugs are silent-until-exploited, so this needs explicit verification, not just "it worked when I clicked around."

### 6.2 Server Actions vs API Routes for privileged operations
- Prefer **Server Actions** for form-driven, same-app mutations (card editing, collaboration status changes, withdrawal requests) — they run server-side, can use the server Supabase client bound to the user's session cookies, and avoid hand-rolling a REST-like API surface for internal use.
- Reserve **Route Handlers** (`app/api/.../route.ts`) for: (a) webhooks (Stripe, and any future LinkedIn-provider webhook) which need a stable public URL and raw-body signature verification; (b) endpoints intentionally called from outside the Next.js app (e.g. a future mobile client or third-party integration); (c) anything needing custom response headers/streaming (the Phase 10 AI assistant's streamed response).
- Never expose the service-role key to a Route Handler that's reachable without server-side auth/role verification — every admin-privileged Route Handler must re-derive the caller's identity from the session cookie (via the server Supabase client) before doing anything with a service-role client, exactly mirroring the Server Action rule above.

### 6.3 Session/cookie handling
Implement the `@supabase/ssr` pattern precisely as documented: `middleware.ts` calls `supabase.auth.getUser()` (not just reading a cached cookie) so expired tokens are actively refreshed, writes refreshed cookies onto both `request.cookies` (for downstream Server Components in the same request) and the outgoing `response.cookies`. Scope middleware's `matcher` to skip static assets and the `(marketing)`/`(public)` route groups where no session is required, to avoid unnecessary auth overhead on public/SEO pages.

### 6.4 Webhook signature verification (Stripe, Phase 7b)
Every webhook Route Handler must: read the **raw request body** (not JSON-parsed — signature verification requires the exact byte payload), verify it against the `Stripe-Signature` header using the webhook signing secret (`STRIPE_WEBHOOK_SECRET`, server-only env var, distinct per environment), reject with 400 on verification failure before touching any business logic, and be idempotent (Stripe retries webhooks — use the event `id` to dedupe processed events, e.g. an `stripe_events_processed` table with a unique constraint on event id).

### 6.5 Rate limiting for public endpoints
Public-facing surfaces needing protection: `/creators/[handle]` (scraping/enumeration risk), any future public "contact this creator"/booking-inquiry form, the sign-up endpoint (credential-stuffing/bot-signup risk), and referral-link redemption endpoints (fraud vector, see 6.6). Recommend an edge-friendly rate limiter (e.g. Upstash Redis + `@upstash/ratelimit`, since it works cleanly from Next.js middleware/edge runtime without a persistent server process) keyed by IP + route, with stricter limits on write endpoints (sign-up, contact forms, referral redemption) than on read endpoints (public card views).

### 6.6 Input validation and abuse prevention for the affiliate/referral mechanic
- **Zod at every server boundary**: define request/response schemas in `lib/validations/` per domain (`affiliateSchema`, `collaborationSchema`, `payoutMethodSchema`, etc.) and parse *all* Server Action/Route Handler inputs through them before touching the database — never trust client-supplied shape even from your own forms, since Server Actions are callable directly (not just from the rendered form).
- **Self-referral prevention**: at referral-redemption time, reject if `referred_profile_id === referrer_profile_id`, and additionally flag/reject if the referred account shares strong identity signals with the referrer (same verified email domain pattern is weak for consumer email but same payout bank-account/Stripe Connect identity, or same device/IP fingerprint at signup, are stronger signals) — store these signals but treat automatic hard-blocking conservatively (false positives block legitimate users) versus flagging for manual review for ambiguous cases.
- **Activation-event integrity**: since the creator-referral reward is keyed to "first completed paid collaboration" (not signup), the `activation_event_at` write must happen only from the same trusted server-side code path that transitions a `collaborations.status` to `completed` with a real, non-zero `agreed_price` — never settable directly by client input — to prevent gaming the reward window via a fake/zero-value "completed" collaboration.
- **Reward payout gating**: affiliate rewards land in `earnings_ledger` with `status='pending'` and should require the underlying collaboration's payment to have actually cleared (once Stripe is live) before transitioning to `available`, mirroring standard marketplace fraud-prevention (don't pay out on money you haven't actually received).
- General velocity/anomaly monitoring: cap referral-link generation per account per time window, and log referral redemptions with enough metadata (IP, user agent, timestamp) to support after-the-fact fraud investigation without over-collecting PII.

### 6.7 Secrets management
- `.env.local` (git-ignored) for local dev; platform-native secret storage (Vercel Environment Variables, or equivalent) for deployed environments — never commit real keys, and keep a checked-in `.env.example` listing required variable *names* only.
- Strict `NEXT_PUBLIC_*` discipline: only `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (both intentionally public/anon-scoped by Supabase's design) are ever prefixed `NEXT_PUBLIC_`. `SUPABASE_SERVICE_ROLE_KEY`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, and any future LinkedIn-provider API key must never carry that prefix and must never be imported into any file that's part of a Client Component's bundle (a useful guardrail: keep all service-role/secret-key usage physically confined to files under `lib/supabase/server.ts` / route handlers / Server Actions, and consider an ESLint rule or code-review checklist item that flags service-role imports outside those paths).
- Bank-account details entered for `payout_methods` (bank transfer path) should not be stored as plaintext columns even pre-Stripe — either avoid persisting full account numbers at all in Phase 1/7 mock mode (store only a masked/last-4 representation for UI purposes) or, once real payouts exist, delegate actual bank-detail custody to a PCI/financial-compliant processor (Stripe's own bank-account tokenization) rather than the app's own database.
